## Сценарии

### 1. Владелец: от создания типа встречи до записи в списке

1. Владелец открывает страницу управления и создаёт тип встречи — указывает название, описание и длительность (например, «Консультация», 30 минут).
2. Новый тип встречи появляется в публичном списке — гости могут записываться по нему.
3. Гость бронирует свободный слот по этому типу (сценарий 2) — встреча сохраняется в базе.
4. В списке предстоящих встреч владельца появляется запись: тип встречи, дата и время, имя и email гостя.

### 2. Гость: запись на звонок

1. Гость заходит на публичную страницу без регистрации и выбирает тип встречи.
2. Открывается календарь на ближайшие 14 дней. Гость выбирает день и видит свободные слоты — слот длится столько, сколько выбранный тип встречи.
3. Гость выбирает свободный слот, указывает имя и email и подтверждает запись.
4. Слот становится занятым: это же время больше нельзя забронировать, даже другим типом встречи. Встреча появляется в списке владельца.

## Деплой

Приложение публикуется одним Docker-образом: multi-stage-сборка (фронт → статический бинарь Go с embed-фронтом → `distroless/static:nonroot`). Платформа передаёт порт через переменную окружения `PORT`, healthcheck — `/health`.

### Docker

```bash
mise run docker-build     # docker build -t call-calendar-387 .
docker run --rm -p 8080:8080 call-calendar-387   # http://localhost:8080/health
```

Порт задаётся через `PORT` (по умолчанию 8080), файл SQLite — через `DB_PATH` (в образе `/data/calls.db`).

### Подключение MCP-сервера Render

Управление деплоем идёт через [Render MCP](https://render.com/docs/mcp-server) из конфигурации проекта (`opencode.json`), без секретов в репозитории:

```json
"render": {
  "type": "remote",
  "url": "https://mcp.render.com/mcp",
  "codemode": false,
  "headers": {
    "Authorization": "Bearer {env:RENDER_API_KEY}"
  }
}
```

Аутентификация — API-ключом Render (OAuth-сервер Render не поддерживает dynamic client registration, поэтому ключ надёжнее). Ключ живёт только в окружении оператора:

```bash
# dashboard.render.com → Account Settings → API Keys → Create API Key
export RENDER_API_KEY=rnd_...
opencode mcp list    # должно показать: ✓ render connected
```

Сервис `call-calendar-387` собирается из репозитория `mmurzin/ai-for-developers-project-387` (ветка `main`) по Dockerfile и обновляется автоматически на каждый пуш. Публичный URL назначает Render.

### Ограничение хранения данных

Демо-стенд работает с **эфемерным хранилищем**: SQLite-файл живёт в файловой системе контейнера и пропадает при каждом передеплое или рестарте — Записи не переживают обновление сервиса. Персистентность (том/диск платформы) сознательно не подключена. Чтобы стенд после вайпа не требовал ручной настройки, при старте на пустой базе сервер сам создаёт два дефолтных Типа звонка (`intro` — Интро-звонок, 15 минут; `consult` — Консультация, 30 минут), см. #26; непустая база не трогается.

Free-инстанс Render засыпает после ~15 минут без трафика: первый запрос после сна может ждать 30–60 секунд (cold start) — это не ошибка, ссылка живая.

## Агент OpenCode в комментариях

В issues и PR работает ИИ-агент [opencode](https://opencode.ai): комментарий с `/oc …` или `/opencode …` запускает его на GitHub Actions (воркфлоу [.github/workflows/opencode.yml](.github/workflows/opencode.yml)).

- **Событие**: `issue_comment` и `pull_request_review_comment`, оба — только `types: [created]`.
- **Модель**: `zai-coding-plan/glm-5.3` (GLM 5.3 по подписке Z.AI Coding Plan); ключ лежит в GitHub Secrets Actions под именем `ZHIPU_API_KEY`.
- **Назначение**: разобрать и объяснить issue, ответить по коду в ревью, внести правки по просьбе — агент читает тред и репозиторий целиком, следует `AGENTS.md` и `docs/agents/` из чекаута (на свежем раннере доступны те же скиллы и настройки GitHub Issues, что и локально).
- **Результаты**: ответ агента приходит комментарием в тот же тред с ссылкой на сессию (share); задачам с правками сопутствуют ветка вида `opencode/issue<N>-<дата>` и PR от лица приложения.
- **Команды (mentions)**: `/opencode,/oc` — заданы явно во входах экшена.
- **Share**: включён (`share: "true"`) — к ответу прикладывается ссылка на полную сессию, чтобы разбирать работу агента без логов Actions.
- **Авторизация**: GitHub App [opencode-agent](https://github.com/apps/opencode-agent), установленная на репозиторий; экшен обменивает OIDC-токен раннера на токен приложения, поэтому у job заданы `contents: read` + `id-token: write`, а `actions/checkout` — `persist-credentials: false`. Альтернативный агент не используется: сценарии «объясни/почини/поревьюй по комментарию» закрывает штатная интеграция opencode.
- **Безопасность**: запуск только для `OWNER`/`MEMBER`/`COLLABORATOR`; комментарии ботов игнорируются (`user.type != 'Bot'`); код из PR не выполняется (checkout только default branch); комментарии от авторов недоверенных fork не проходят гейт — задание и секрет не запускаются вовсе. Тайм-аут job — 30 минут, конкурентность — один запуск на issue/PR (повторная команда отменяет предыдущую). Используемые экшены (`actions/checkout`, `anomalyco/opencode/github`) запинены по SHA.
- **Живой пример**: [issue #2](https://github.com/mmurzin/ai-for-developers-project-387/issues/2) — первый прогон интеграции: `/oc explain this issue` → [успешный запуск воркфлоу](https://github.com/mmurzin/ai-for-developers-project-387/actions/runs/43752116572), ответ агента — в том же треде. Запуски видны в разделе Actions под именем `opencode`.
- **Линт воркфлоу**: триггер `issue_comment` попадает под правило `dangerous-triggers` jactionlint. Исключение сознательно задокументировано в [.github/jactionlint.yaml](.github/jactionlint.yaml) — причина (гейт автора, отсев ботов, checkout только default branch, пин экшена по SHA) и дата пересмотра `2027-02-15`; после неё правило `expired-ignore` уронит `mise run lint`, пока исключение не продлят или не уберут.

### Как звать агента: шпаргалка

```text
/oc разбери обращение по скиллу triage, предложи следующий шаг, код пока не меняй
        ↓ агент: бриф (вопросы → ответы обычными комментариями) — СТОП
        ↓ выбор за владельцем:
/oc реализуй бриф из треда                          ← маленькая задача (одна сессия)
/oc примени скилл grill-with-docs по этому issue    ← большая: дальше to-spec → to-tickets
```

- Стоп-слова, которые агент уважает: «код не меняй», «бриф и стоп».
- «Продолжай» / «как договаривались» — **не** команда на реализацию: без явного «реализуй»/`/implement` агент останавливается на брифе.
- Issue закрывает и PR мерджит владелец; агент не вписывает `Closes #N` сам.

## Периодический аудит прода агентом

Воркфлоу [prod-audit](.github/workflows/prod-audit.yml) раз в сутки (06:23 UTC) и вручную запускает ИИ-агента opencode (та же модель `zai-coding-plan/glm-5.3`, что и в комментариях) с промптом аудита демо-стенда. В отличие от `deploy-drift`, который сверяет метаданные деплоев с `main`, агент проверяет **фактическое поведение прода по HTTP** и оставляет по находкам наблюдаемый след — issue.

- **Расписание и дисциплина запусков**: `cron "23 6 * * *"` (не чаще раза в сутки) + `workflow_dispatch`; `concurrency` исключает параллельные аудиты (новый ждёт очереди, а не обрывает текущий), тайм-аут job — 15 минут.
- **Что проверяет агент**: HTTP-смоук — `/health` (статус + `Content-Type: application/json` + тело `{"status":"ok"}`, а не просто «200»), `/` (SPA-индекс с названием продукта и собранными ассетами), `/api/call-types`, 404-catch-all для неизвестных `/api/*`; холодный старт; Render API — сервис не приостановлен, последний деплой `live` и совпадает с HEAD. Полный промпт с фиксированными fingerprint'ами — в файле воркфлоу.
- **Права**: job выдаёт агенту `issues: write` (создание issue и комментариев) и `contents: read`. Read-only по содержимому — не обещание в промпте, а физическое ограничение: отчёт уходит в artifact запуска, в репозиторий попасть не может.
- **Находки**: issue с меткой [`audit:prod`](https://github.com/mmurzin/ai-for-developers-project-387/issues?q=label%3Aaudit%3Aprod), заголовок вида `[prod-audit] <fingerprint>: …`. Перед созданием агент обязан проверить открытые issue: повторная находка с тем же fingerprint становится комментарием «Воспроизводится…» в существующем issue, а не дублем.
- **Учебный режим**: вход `study_probe` у `workflow_dispatch` включает заведомо падающую проверку с пометкой `[учебное]` — страховка на случай полностью зелёного прода, когда для демонстрации сценария «issue по находке» нужна явно обозначенная учебная задача. На расписании всегда выключен; в запусках ниже не понадобился — нашлась реальная находка.

### Результаты запусков

- [Запуск 1](https://github.com/mmurzin/ai-for-developers-project-387/actions/runs/43929765241) — ручной, из `main`: 6 проверок зелёные, одна реальная находка — [issue #12](https://github.com/mmurzin/ai-for-developers-project-387/issues/12): главная прода отдаёт `<title>vite-app</title>` — со времён скаффолда Vite не правился `frontend/index.html` (правильный титул есть только в placeholder `internal/web/dist/index.html`). Отчёт — artifact `prod-audit-report` запуска, резюме агента — в логах шага «Run OpenCode».
- [Запуск 2](https://github.com/mmurzin/ai-for-developers-project-387/actions/runs/43930507380) — ручной повтор тем же составом: находка воспроизвелась, дубль **не** создан — агент [прокомментировал](https://github.com/mmurzin/ai-for-developers-project-387/issues/12#issuecomment-6925526132) существующий issue #12 с датой и ссылкой на запуск.
- Холодный старт в обоих прогонах не наблюдался (стенд был тёплым, ~0.25 с) — на суточном расписании первый запрос будет будить уснувший free-инстанс, и это уйдёт в отчёт как наблюдение `cold-start`.

### Выводы о работе агента

1. **Агент вышел за рамки чек-листа.** Находку `spa-index` он не просто зафиксировал, а локализовал до строки (`frontend/index.html`) и отличил «дрейф деплоя» от «недоработка в репозитории» — сверился с исходником. Для мониторинга «статус-кодов» это недостижимый уровень: проблема была в том, чего curl сам не знает (ожидаемый титул), а не в том, что что-то упало.
2. **Инструкции агент соблюдает буквально — поэтому промпт и есть интерфейс.** Дедуп, запрет коммитов, формат заголовков — всё исполнено; но работает это потому, что fingerprint'ы жёстко перечислены в промпте. Свобода в формулировках сломала бы дедуп: LLM каждый раз озаглавила бы находку по-разному.
3. **Права важнее обещаний.** «Отчёты не попадают в коммиты» держится на `contents: read` у job, а не на доброй воле модели — такой разделённый доступ стоит делать правилом для любых агентных воркфлоу.
4. **Цена вопроса.** Прогон — около 3 минут агента; для ежечасного аудита дорого и шумно, для суточного — дёшево. Реальную пользу показал уже первый запуск: дефект, который не видят ни тесты (smoke проверяет только наличие index), ни deploy-drift (деплой-то успешный).
